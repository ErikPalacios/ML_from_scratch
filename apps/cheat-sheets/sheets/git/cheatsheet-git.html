Nombres y números de bolsillo

¿Qué estados, nombres y números de git y de GitHub Actions conviene saberse de memoria para leer un repo o una ejecución de CI (las pruebas automáticas de cada cambio) en segundos?

Sintaxis con variables

git status -sb

La foto rápida del repo. Cada archivo lleva dos letras: la izquierda es el staging (lo que entra en el próximo commit, la próxima foto del proyecto que guardes) y la derecha, el working tree (tus archivos en disco). La primera línea dice tu rama (la etiqueta que avanza con tus commits), la rama del remoto a la que está conectada (su copia en GitHub) y cuántos commits tienes de más o de menos que ella: [ahead 1, behind 1].

git log --oneline --graph --all -n n

La historia, un commit por línea: el SHA corto (el nombre del commit), entre paréntesis las etiquetas que apuntan ahí y el mensaje. HEAD -> main es dónde estás; origin/main es lo último que viste del remoto (la copia del repo en GitHub).

git rev-parse --short ref

Traduce un nombre (HEAD, main, origin/main, HEAD~1) al SHA de su commit; sin --short, da los 40 caracteres. Con --short acepta un solo nombre por vez y da 7 caracteres en un repo chico, más cuando el repo crece. En el C01, el tag (el nombre de versión) de la imagen Docker del gateway son los primeros 7: --short=7 los da aunque el repo crezca, como ${GITHUB_SHA::7} en CI.

git reflog -n n

El diario de HEAD en tu máquina: cada vez que HEAD se mueve (un commit, un cambio de rama, un reset que mueve la rama a otro commit, un merge o un rebase que juntan ramas) queda una línea HEAD@{n}. No viaja con push (subir al remoto) ni con clone (copiar el repo). Si un commit "desapareció", búscalo aquí.

$ git status -sb

M  gateway/app/main.py

$ git log --oneline --graph --all
* 4f4fd71 (HEAD -> feat/gateway-timeout) gateway: deadline total de 250 ms
* 3fb9f47 (origin/feat/gateway-timeout) gateway: bajar INFER_TIMEOUT_S a 120 ms

  • [ahead 1]: tienes 1 commit (4f4fd71) que el remoto no tiene; git push lo sube. [behind 1] sería lo contrario: te falta 1, y git pull lo trae.
  • main.py tiene la M a la izquierda: el cambio está en staging y entra en el próximo commit.
  • preprocess.py tiene la M a la derecha: cambió en disco, pero el próximo commit no lo lleva hasta que hagas git add.
  • ?? .env: un archivo que git no sigue. Es un secreto local: va al .gitignore (la lista de lo que git ignora), nunca a un commit (sección Día a día).
  • En el log, HEAD -> feat/gateway-timeout es dónde estás y origin/… es tu última foto del remoto. main y origin/main están en el mismo commit: al día, según tu último fetch.

Cómo recordarla

Lee git status -sb en dos columnas: izquierda = staging, derecha = disco. HEAD es "estás aquí", una rama es una etiqueta con un SHA y origin/main es tu última foto del remoto. Números: SHA de 40 hex, reflog 90 / 30 días, job de Actions 360 min.

Trampa

Leer origin/main como el remoto en vivo: es tu foto del último fetch y puede tener días. git status no le pregunta nada al remoto, así que "up to date" puede ser falso: corre git fetch antes de mirar. Y creer que push sube el reflog o el stash (los cambios que guardaste aparte con git stash): los dos viven solo en tu máquina.

Cómo arreglarlo y confirmarlo

Si un archivo entró (o no entró) al commit por sorpresa, lee git status -s antes de commitear: la columna izquierda es lo que entra. Para sacar algo del staging: git restore --staged {ruta}.

Probado de verdad en una carpeta de prueba (git 2.50.1). Los SHAs y las rutas cambian en cada máquina.

La cadena: de tu cambio al deploy

¿Qué pasa, en orden, desde que editas un archivo hasta que esa versión recibe tráfico en producción, y quién hace cada paso?

Sintaxis con variables

git switch main && git pull
git switch -c rama

Cada cambio va en su propia rama (una etiqueta que avanza con cada commit, cada foto del proyecto que guardas), creada desde la versión más nueva de main, la rama principal. Los nombres dicen qué es: feat/… para algo nuevo, fix/… para un arreglo.

git add ruta
git commit -m "mensaje"

Eliges qué entra (add) y guardas la foto con un mensaje (commit). El commit vive solo en tu máquina hasta el push.

git push -u origin rama

Sube la rama a GitHub (origin es el nombre corto del repo del equipo). -u la conecta con origin/rama, su copia en GitHub, la primera vez; después basta git push. GitHub responde con líneas remote: que traen el link para abrir el pull request (PR: la propuesta de juntar tu rama con main).

git rev-parse --short=7 HEAD

Después del merge (cuando el PR entra a main), parado en main: los primeros 7 caracteres del SHA (el nombre único) del commit que construye CD (la entrega continua). Son el tag de la imagen, classifier-gateway:sha, igual que ${GITHUB_SHA::7} en CI (integración continua): de un pod (una copia del servicio corriendo en Kubernetes) llegas al código exacto. Sin =7, git da más caracteres cuando el repo crece.

  • El commit vive solo en tu máquina hasta el push. -u conecta tu rama con origin/feat/gateway-timeout: desde ahí, git push y git pull saben a dónde ir. Contra GitHub, el push imprime además líneas remote: con el link del PR.
  • El CI de un PR prueba un merge de prueba de tu rama con main (refs/pull/N/merge), no tu rama sola. Y si el PR tiene conflictos (cambios que chocan con los de main), los workflows de pull_request no corren.

Cómo recordarla

Git guarda, GitHub revisa, Actions prueba y construye, Kubernetes despliega. Tu parte termina en el push y el PR; desde el merge, todo es automático y deja rastro: commit → check → imagen :SHA → rollout.

Trampa

Creer que el merge es el deploy. El merge solo cambia main: a producción llega la imagen con el SHA de ese commit, cuando CD la construye, la sube y el manifest la apunta. Y abrir el PR con conflictos: los workflows de pull_request no corren hasta que los resuelvas, así que no hay checks que mirar.

Qué es Git: fotos, etiquetas y tres zonas

¿Qué guarda git en realidad, qué es una rama, qué es HEAD y por qué hay un paso entre editar y commitear?

Sintaxis con variables

git init -b rama

Crea la carpeta .git: ahí vive el repositorio, con todos los commits (las fotos del proyecto), las ramas (etiquetas que avanzan con cada commit) y los tags (etiquetas fijas). -b main le pone nombre a la primera rama; sin eso, git usa init.defaultBranch y, si no está configurada, master (Git 3.0, todavía sin fecha, la cambiará a main). GitHub llama main a la rama por defecto.

git cat-file -p ref

Muestra por dentro un objeto (cada cosa que git guarda: un commit, una carpeta o un archivo). Un commit tiene su tree (la foto de los archivos), su parent (el commit anterior), autor y committer (quién lo escribió y quién lo guardó, con sus fechas) y el mensaje.

git branch rama
git rev-parse rama main

Crear una rama escribe un archivo con un SHA (el nombre de 40 caracteres de un commit): no copia ningún archivo del proyecto. Recién creada, apunta al commit donde estás (HEAD, el "estás aquí" de git); si estás en main, al mismo que main.

git switch --detach ref

Pone en disco una foto vieja sin mover ninguna rama: quedas en detached HEAD (HEAD apunta a un commit, no a una rama). Sirve para mirar o probar; git switch - te devuelve a tu rama.

El día a día: clone, status, add, commit, diff, log, push, pull, fetch y .gitignore

¿Qué comandos usas todos los días, qué toca cada uno (tus archivos, tu repo o el remoto) y qué haces cuando push o pull se niegan?

Sintaxis con variables

git clone url
cd carpeta

Copia el repo con toda su historia a una carpeta nueva, registra el remoto (la copia en GitHub) como origin y te deja en la rama por defecto (casi siempre main), conectada con origin/main: tu copia local del main de GitHub. La URL puede ser SSH o HTTPS, dos formas de conectarte; cómo autenticarte está en la sección GitHub.

git status
git diff
git add ruta
git diff --staged
git commit -m "mensaje"

El ciclo de cada commit (cada foto que guardas): mira qué cambió, revisa el diff (las líneas que cambiaron), elige con add y revisa lo elegido antes de guardar. git add -p te deja elegir pedazos de un archivo.

git fetch
git status -sb
git pull --rebase
git push

Sincronizar. fetch baja lo nuevo y solo mueve origin/…: tus archivos no cambian. pull = fetch + juntar con tu rama; --rebase pone tus commits locales encima de los del remoto, sin un commit de merge (uno extra que junta las dos historias). push sube lo tuyo; la primera vez de una rama, git push -u origin rama.

git config --global pull.ff only

Decide una vez qué hace git pull cuando las ramas divergieron (cada una tiene commits que la otra no). Con pull.ff only solo avanza si no hay nada que mezclar y, si divergieron, se niega y eliges tú con git pull --rebase. Sin ninguna config también se niega (desde Git 2.33.1): fatal: Need to specify how to reconcile divergent branches.

git rm --cached ruta

4

Deshacer: restore, reset, revert, amend, stash y reflog

¿Cómo deshaces cada tipo de error, de un archivo sin guardar a un commit que ya está en main, y cómo recuperas un commit que creías perdido?

Sintaxis con variables

git restore ruta
git restore --staged ruta

Para archivos. Sin opciones, descarta lo que cambiaste en disco (vuelve a la versión del staging: la de tu último git add o, si no hiciste add, la del último commit): no tiene deshacer. Con --staged, saca el archivo del staging y tu disco no cambia. Reemplazan a git checkout -- ruta y a git reset ruta.

git commit --amend --no-edit

Rehace el último commit con lo que hay en staging (con -m "…", también cambia el mensaje). Sale un commit nuevo, con otro SHA: úsalo solo si no hiciste push.

git reset modo HEAD~n

Mueve la rama n commits atrás. --soft: los cambios quedan en staging; --mixed (el default): quedan en disco, fuera del staging; --hard: se borran de staging y disco, junto con lo que no habías commiteado. Los commits siguen en el reflog (el historial local de HEAD).

git revert sha
git revert -m 1 sha_merge

Crea un commit nuevo que deshace otro. No reescribe nada: es el camino después de un push, y el rollback (volver a la versión anterior) por PR en main. Para revertir un merge commit, -m 1 dice que la línea principal es su primer padre.

git stash push -u -m "nota"
git stash list
git stash pop

Guarda tus cambios sin commit en una pila (el stash) y deja tu disco limpio. -u incluye también los archivos nuevos que git todavía no sigue (untracked); sin él, quedan afuera. pop los devuelve y borra la entrada; si hay conflicto, la entrada se queda.

git reflog
git branch rescate HEAD@{n}

El reflog lista dónde estuvo HEAD. Un commit "perdido" tras un reset o un rebase sigue ahí (al menos 30 días por defecto): ponle una rama encima y queda a salvo.

  • Los checks de un PR no prueban tu rama sola: corren sobre un merge de prueba de tu rama con main (refs/pull/N/merge). Por eso un PR puede fallar en CI aunque tu rama sola pase: combinada con el main de ese momento, es otro código.

Rama → push → PR → checks y review → merge. Quien dice que no es la regla de la rama: sin aprobación o con tests en rojo, el merge no se habilita.

Anatomía de un workflow de Actions

¿Qué partes tiene un workflow, en qué orden corre cada cosa y cómo se pasan datos entre sí?

Sintaxis con variables

name: nombre
on:
  evento:
    branches: [rama]
permissions:
  contents: read
jobs:
  job:
    runs-on: runner
    timeout-minutes: minutos
    steps:
      - uses: dueño/acción@{versión}
        with:
          input: valor
      - run: comando

Un workflow es un archivo YAML en .github/workflows/. on dice cuándo corre. Cada job corre en su propio runner (la máquina que lo ejecuta; los de GitHub son una máquina nueva y limpia en cada job) y sus steps (pasos) corren en orden dentro de esa máquina.

  job_b:
    needs: [job_a]
    if: github.event_name == 'evento'

Sin needs, los jobs corren en paralelo. Si job_a falla o se salta, job_b también se salta, salvo que su if use always().

    outputs:
      salida: ${{ steps.paso.outputs.salida }}
    steps:
      - id: paso
        run: echo "salida=valor" >> "$GITHUB_OUTPUT"
# en un job con needs: [job] se lee ${{ needs.job.outputs.salida }}

Un paso deja un dato escribiendo en el archivo $GITHUB_OUTPUT (reemplaza al viejo ::set-output). Otro job lo lee solo si nombra al primero en needs.

on:
  workflow_dispatch:
    inputs:
      input:
        type: tipo
        required: true

Agrega el botón Run workflow, que solo aparece si el archivo está en la rama por defecto. Hasta 25 inputs; se leen con inputs.input.

  pull_request:
  push: { branches: [main] }

  contents: read
jobs:
  tests:
    runs-on: ubuntu-24.04

      run: { working-directory: reference/c01/gateway }

Tests en CI: Python, caché, matrix y checks obligatorios

¿Cómo corres pytest en cada PR, rápido y sin que un test rojo llegue a main?

Sintaxis con variables

- uses: actions/setup-python@v7
  with:
    python-version: "versión"
    cache: pip
    cache-dependency-path: carpeta/requirements*.txt
- run: pip install -r carpeta/requirements-dev.txt
- run: pytest --junit-xml=reporte.xml

En CI (integración continua: las pruebas automáticas que corren con cada push y cada PR), la caché de pip guarda los paquetes que pip bajó, no el entorno instalado: el pip install corre igual, pero saca los paquetes de la caché en vez de bajarlos. La versión va entre comillas: en YAML, 3.10 sin comillas es el número 3.1.

- uses: actions/cache@v6
  with:
    path: carpeta_cache
    key: so-herramienta-${{ hashFiles('archivo_lock') }}
    restore-keys: |
      so-herramienta-

Una caché (archivos que se guardan entre runs para no repetir trabajo) se busca por su key. Si coincide exacta es un hit; si no, restore-keys trae la más reciente que empiece igual. Una caché no se reescribe: si cambia el archivo, cambia la key y se guarda otra.

strategy:
  fail-fast: false
  matrix:
    python-version: ["v1", "v2"]
steps:
  - uses: actions/setup-python@v7
    with:
      python-version: ${{ matrix.python-version }}

Una matrix repite el job por cada combinación de valores, y cada copia es un check aparte (su propio resultado en el PR), como tests (3.13). Con fail-fast: true, el default, el primer rojo cancela a los demás.

- if: failure()
  uses: actions/upload-artifact@v7
  with:
    name: nombre
    path: ruta
    retention-days: días

Un artifact es un archivo del run que bajas desde su página (en un zip). Sin retention-days, dura lo que diga el repo: 90 días por defecto. if: failure() lo sube solo cuando algo falló.

Secretos, permisos y OIDC: entrar a AWS sin llaves

¿Con qué permisos corre tu workflow, dónde guardas lo secreto y cómo entra a AWS sin guardar ninguna llave?

Sintaxis con variables

permissions:
  contents: read
jobs:
  job:
    permissions:
      contents: read
      permiso: write

El GITHUB_TOKEN es la llave temporal que GitHub le da a cada job para hablar con tu repo. permissions fija qué puede hacer: lo que no nombras queda en none, y un bloque en el job reemplaza al de arriba, así que ahí repites contents: read.

- name: paso
  env:
    VARIABLE: ${{ secrets.SECRETO }}
    OTRA: ${{ vars.VARIABLE_CONFIG }}
  run: comando

Un secret es un valor cifrado que guardas en Settings; en el log aparece como ***. Una variable (vars) es configuración no secreta y se ve tal cual. Las dos entran por env, nunca pegadas en el comando.

permissions:
  id-token: write
  contents: read
steps:
  - uses: aws-actions/configure-aws-credentials@{sha_acción} # v6.3.0
    with:
      role-to-assume: arn:aws:iam::cuenta:role/rol
      aws-region: región

OIDC (OpenID Connect): el job pide un token firmado por GitHub que dice quién es (repo, rama o environment, un entorno con reglas como produccion), y AWS lo cambia por credenciales de un rol (una identidad con permisos que el job toma prestada) que vencen solas, en 1 hora por defecto. id-token: write solo permite pedir ese token.

"Condition": {
  "StringEquals": {
    "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
    "token.actions.githubusercontent.com:sub": "repo:org/repo:ref:refs/heads/rama"
  }
}

La trust policy del rol dice qué tokens pueden asumirlo. El sub es el campo del token que dice quién lo pide; IAM (el servicio de permisos de AWS) rechaza la política si no lo revisa o si acepta cualquiera (*). Con environment, el sub pasa a ser repo:org/repo:environment:entorno. Hay dos formatos: un repo creado, renombrado o transferido después del 15 de julio de 2026 (o que eligió el formato nuevo) agrega los IDs numéricos del dueño y del repo, como repo:acme@123/classifier@456:ref:refs/heads/main. Copia el que usa tu repo: con el otro, AWS responde Not authorized.

CD (continuous delivery, entrega continua) es llevar a producción, por etapas, lo que CI (las pruebas automáticas de cada cambio) ya probó. Hay dos caminos; este es el primero. GitOps, lado de CI: GitOps quiere decir que el estado de producción vive en git: los manifests (los YAML de Kubernetes) dicen qué imagen corre. Después del push a ECR, el job cambia la línea image: del manifest: el tag dice de qué commit salió y el digest (la huella sha256 del contenido) fija los bytes exactos. Luego abre o actualiza un pull request con el token de una GitHub App (una identidad de máquina con permisos propios). Con ese token, los checks del PR corren solos. Desplegar es hacer merge de ese PR.

apiVersion: argoproj.io/v1alpha1

GitOps, lado del cluster. Argo CD corre dentro del cluster, compara lo que dice main con lo que corre y aplica la diferencia (un sync). selfHeal deshace los cambios hechos a mano en el cluster; prune borra lo que sacaste de git. Los dos vienen apagados si no los pones.

deploy:
  needs: job_imagen
  environment: entorno
  concurrency: { group: deploy-servicio-entorno, cancel-in-progress: false }
  steps:  # antes: el rol de deploy por OIDC (sección 8), aws eks update-kubeconfig y un kubectl de la versión del cluster

Estilo kubectl, el segundo camino y el de gateway.yml: el job empuja el cambio al cluster. Un environment (un entorno con nombre, con reglas y secretos propios) lo deja en Waiting hasta que apruebe alguien de la lista de required reviewers. concurrency deja un solo deploy a la vez en ese grupo. set image cambia solo la imagen, por digest; con kubectl apply -f, el manifest tiene que traer ya la imagen nueva. Si los pods nuevos no quedan listos, rollout status falla con exceeded its progress deadline (600 s sin avance, por defecto) y el job queda rojo; Kubernetes no vuelve atrás solo: los pods viejos siguen sirviendo.

Rollback = revert: un commit nuevo que deshace el del deploy. La historia queda completa: qué se desplegó, cuándo y cómo se volvió. Un merge commit tiene dos padres, así que -m 1 dice que el lado bueno es main. El botón Revert de un PR mergeado hace lo mismo: abre un PR nuevo.

CI construye, git decide, el cluster copia. Desplegar es un merge que cambia una línea; volver es un revert de ese merge. El environment pone a una persona en el medio y concurrency pone a los deploys en fila.

Runners: GitHub-hosted o self-hosted (la T4 del C01), labels, timeouts y costos

¿En qué máquina corre cada job, cuánto puede durar, cuánto cuesta y cuándo conviene una máquina propia, como la T4 del C01?

Sintaxis con variables

jobs:
  job:
    runs-on: imagen
    timeout-minutes: min

Un runner es la máquina que ejecuta un job. Con una imagen de GitHub (GitHub-hosted), cada job recibe una VM (máquina virtual) nueva. timeout-minutes corta el job si se pasa: el default es 360 min (6 h), que también es el máximo en GitHub-hosted.

runs-on: [self-hosted, so, arq, label]

Un runner self-hosted es una máquina tuya con el programa del runner instalado. Las labels son etiquetas: el job va a un runner que tenga todas las que pide. self-hosted, el sistema y la arquitectura las pone el runner solo; las demás son tuyas.

./config.sh --url https://github.com/org/repo --token token_registro --labels label --ephemeral --unattended
./run.sh

Registrar el runner, en la máquina. El token de registro sale de Settings → Actions → Runners → New self-hosted runner (o de la API) y vence en 1 h. Con --ephemeral, el runner toma un job y se desregistra: la base para crear una máquina por job y apagarla al final.

runs-on:
  group: grupo
  labels: [label]

En una organización, los runners se juntan en runner groups (grupos con su lista de repos permitidos). Con group y labels, el runner tiene que cumplir las dos cosas. Un larger runner de GitHub (más grande, o con GPU) se elige por su grupo o por su nombre, que es su label.

Ejemplo real · C01: qué job corre en qué máquina

YAMLIlustrativo, armado con los pasos del curso: reference/c01/README.md (engine e imagen en una g4dn.xlarge con T4), M10 · CI/CD (runner con T4 que se prende solo para el job) y C01 · costo. Specs, límites y precios de docs.github.com (octubre de 2026).
# Extractos de gateway.yml y triton-modelo.yml. Ilustrativos, armados con los pasos del curso: el C01 no trae workflows.
# gateway.yml: máquinas de GitHub, una VM nueva por job
jobs:
  tests:
    runs-on: ubuntu-24.04          # x64: linux/amd64 sin emulación; fija la versión, no ubuntu-latest
    timeout-minutes: 10            # 24 tests tardan segundos: 10 min ya es una falla
    # …
  imagen:
    runs-on: ubuntu-24.04
    timeout-minutes: 20
    # …
---
# triton-modelo.yml: la T4 propia, a mano o desde el pipeline del modelo
on:
  workflow_dispatch:               # nunca pull_request: un PR no corre código en la T4
jobs:
  engine-e-imagen:
    runs-on: [self-hosted, linux, x64, gpu-t4]   # todas las labels: solo la g4dn las tiene
    timeout-minutes: 120           # sin esto, un trtexec colgado retiene la T4 los 360 min del default
    # … build_engine.sh, docker build triton/, paridad, push y registro
  • tests e imagen: una VM nueva por job. En un repo privado tiene 2 vCPU, 8 GB de RAM y 14 GB de disco (4 vCPU y 16 GB si el repo es público). Es x64, así que linux/amd64 se construye sin emulación.
  • Lo decisivo: el engine de TensorRT solo se construye en una T4, y un runner estándar no tiene GPU. Además, la imagen de Triton pesa ≈ 9.2 GB comprimida (cifra del módulo 5) y bastante más en disco: muy justa para los 14 GB que garantiza un runner estándar.
  • La g4dn se registra como runner efímero (--ephemeral): toma un job, se desregistra y la apagas. Para prenderla cuando hay un job en cola: ARC (en Kubernetes) o tu propia automatización con el webhook workflow_job.
  • Costo de una corrida de 40 min (est.): la g4dn on-demand ≈ US$0.526/h → ≈ US$0.35, más el arranque. El runner GPU de GitHub (también una T4) → 40 × US$0.052 = US$2.08, sin máquina que mantener, pero solo en Team o Enterprise Cloud. El curso estima menos de US$10 al mes para este runner.
  • Solo workflow_dispatch: la T4 nunca corre código de un PR. En un repo público, ni pensarlo: cualquiera puede abrir un PR y una máquina persistente guarda lo que el job anterior dejó.
  • timeout-minutes en cada job. En self-hosted podrías subirlo hasta 5 días, pero el GITHUB_TOKEN se renueva solo hasta 24 h (en GitHub-hosted dura lo que el job, como mucho 6 h).

Cómo recordarla

labels eligen, timeout corta, minutos cuestan. GitHub-hosted: una VM limpia por job, gratis en repos públicos. Self-hosted: tu hardware (la T4), tu mantenimiento y tu riesgo; efímero, por workflow_dispatch y nunca en un repo público.

Trampa

un runner self-hosted persistente que corre jobs de pull_request, o cualquiera en un repo público. El código de un PR corre en tu máquina, que no se limpia entre jobs: puede leer credenciales del disco o dejar algo instalado para el próximo job. Y ubuntu-latest se mueve: cuando pase a otra versión de Ubuntu, cambian Python, compiladores y librerías sin que toques el YAML.

Diagnóstico: leer el log, re-run con debug, reproducir en local, tipos de falla

El check se puso rojo: ¿dónde está el error de verdad, qué tipo de falla es, cómo la reproduces en tu máquina y cuándo sirve un re-run?

Sintaxis con variables

gh run list --workflow workflow --branch rama --limit 5

Leer el log: run rojo → job rojo → paso rojo. El error de verdad está arriba de Process completed with exit code N (N es el código con que terminó el comando; 0 es éxito) y casi siempre es el primero, no el último. --log-failed muestra solo los pasos que fallaron; sin gh, lo mismo en la pestaña Actions.

Re-run: vuelve a correr lo que falló con el mismo commit (mismo GITHUB_SHA y GITHUB_REF). --debug (en la web, Enable debug logging) suma el log detallado de cada paso y del runner. Si falla igual, no fue mala suerte.

Trampa

Corre primero

  1. Alguien empujó antes que tú: el remoto tiene commits que no tienes (fetch first) o que bajaste pero no integraste (non-fast-forward).

    Compruébalo: git fetch origin && git status (dice behind o have diverged)

    Arreglo: git pull --rebase (o --no-rebase), resuelve si hay conflictos, corre los tests y vuelve a hacer push. Nunca --force en una rama compartida.

  2. Reescribiste commits que ya estaban en el remoto (amend, rebase, reset) en tu rama del PR.

    Compruébalo: git log --oneline origin/RAMA..HEAD (lo que solo tienes tú) · git log --oneline HEAD..origin/RAMA (lo que solo tiene el remoto)

    Arreglo: Si la rama es solo tuya: git push --force-with-lease, que se niega si el remoto cambió desde tu último fetch. En main o en una rama compartida, nunca.

  3. Una regla del repo lo bloquea: main pide PR y checks (remote: error: GH013 … o GH006 …, y [remote rejected]).

    Compruébalo: las líneas remote: (dicen qué regla) · Settings → Rules → Rulesets

    Arreglo: Empuja a una rama y abre un PR. Si es CI quien empuja a main, que abra un PR (sección 10).

    Compruébalo: las líneas remote: con commit y path · git log -p -1 (si es el último commit)

    Arreglo: Sácalo de los commits antes de empujar: git commit --amend si es el último; git rebase -i SHA~1 si es anterior. Si la credencial es real, rótala.

  3. Hiciste commits en detached HEAD y saliste (Warning: you are leaving 1 commit behind…).

    Compruébalo: el aviso trae el SHA · git reflog

    Arreglo: git branch rescate SHA

  4. En CI es normal: en un pull_request, actions/checkout deja HEAD en el merge commit de prueba, no en una rama; git rev-parse --abbrev-ref HEAD responde HEAD.

    Compruébalo: git status en un paso del job

    Arreglo: En un PR, la rama está en github.head_ref (GITHUB_HEAD_REF); ahí GITHUB_REF_NAME vale N/merge, y solo en un push es la rama. Si un paso tiene que empujar a la rama del PR, haz el checkout con ref: ${{ github.head_ref }}.
