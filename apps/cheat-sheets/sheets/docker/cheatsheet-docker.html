Números y códigos de bolsillo

¿Qué números conviene saberse de memoria para leer un fallo en segundos?

Sintaxis con variables

docker run --rm imagen comando; echo "exit=$?"

El exit code del contenedor llega a tu shell: 125, 126 y 127 los pone Docker, y 255, runc; cualquier otro es de tu proceso. Si el daemon no corre, el CLI sale con 1 (antes de la 29.1.3, docker run daba 125 o 127).

docker ps -a --filter name=contenedor

STATUS dice Exited (137) 5 seconds ago: el código queda ahí aunque el contenedor ya no corra.

docker stop -t segundos contenedor

SIGTERM, espera segundos (10 por defecto en Linux) y después SIGKILL.

Ejemplo real · Parar el gateway del C01 sin cortar requests

bash · zshreference/c01/gateway/Dockerfile (CMD) y reference/c01/k8s/gateway.yaml
# El CMD del gateway drena hasta 20 s tras el SIGTERM (--timeout-graceful-shutdown 20);
# docker stop solo espera 10 s por defecto: dale los mismos 30 s que tiene en k8s
docker stop -t 30 gw

# ¿Cómo terminó? STATUS dice "Exited (código) …"; OOMKilled=true confirma memoria
docker ps -a --filter name=gw
docker inspect -f '{{.State.ExitCode}} {{.State.OOMKilled}}' gw

# En Kubernetes: 45 s de plazo total, y el preStop (sleep 15) gasta 15 antes del SIGTERM
grep -n -e terminationGracePeriodSeconds -e sleep k8s/gateway.yaml
  • --timeout-graceful-shutdown 20 está en el CMD del gateway: es el tiempo que uvicorn se da para terminar los requests en curso.
  • docker stop espera 10 s y manda SIGKILL: con requests en vuelo, al gateway dale -t 30. En compose el equivalente es stop_grace_period (también 10 s por defecto); el docker-compose.yml del C01 no lo fija, así que stop_grace_period: 30s sería un agregado tuyo.
  • 137 con OOMKilled true confirma memoria. Con false suele ser el plazo vencido o un docker kill, pero si nadie hizo stop ni kill no descartes la memoria: containerd puede perder el evento de OOM.
  • Si lo arrancaste con --rm, después del stop ya no existe: para ver su exit code, córrelo sin --rm.
  • Por qué 30: en el clúster manda terminationGracePeriodSeconds: 45, que empieza a contar con el preStop (sleep 15); tras el SIGTERM, a uvicorn le quedan 30 s.

Cómo recordarla

Por encima de 128 (salvo 255), resta 128 y busca la señal: 137 = 9 = KILL (memoria, o se acabó el plazo) y 143 = 15 = TERM. 125, 126 y 127 dicen que Docker no pudo arrancar tu comando: falla de Docker, no es ejecutable, no existe.

Trampa

Leer 137 como "falta de memoria" sin mirar OOMKilled: también da 137 un docker stop cuyo proceso ignoró el SIGTERM durante los 10 s. Y en Mac, buscar /var/lib/docker en Finder: esa ruta vive dentro de la VM.

  2. Paso 2

    Qué deberías ver: exit=137 y, casi siempre, true: sin swap (--memory-swap igual a --memory), el kernel mató a Python al pasar los 32 MB. Si ves false, containerd perdió el evento de OOM; un 137 sin stop ni kill ya apunta a memoria.

  4. Paso 4
    docker run -d --name lab-stop busybox:1.38 sleep 300
time docker stop lab-stop
docker inspect -f '{{.State.ExitCode}}' lab-stop

    Qué deberías ver: Unos 10 s de espera y 137: sleep es el PID 1, no instala handler de SIGTERM y el kernel le descarta la señal; al final llega el SIGKILL.

    Qué deberías ver: Menos de un segundo y 143: docker-init (tini) es el PID 1, le reenvía el SIGTERM a sleep y sleep muere por esa señal (128 + 15).

  6. Paso 6

    Qué deberías ver: Los tres nombres impresos: no queda nada del lab.

Cómo arreglarlo y confirmarlo

El 137 del paso 4 se arregla con un PID 1 que maneje SIGTERM: --init en docker run (init: true en compose), o un servidor que lo atrape (uvicorn, Triton) en un CMD con forma exec. Confírmalo con time docker stop: vuelve en menos de un segundo.

La cadena

¿Qué comandos llevan tu Dockerfile hasta un contenedor corriendo en otra máquina?

Sintaxis con variables

docker build --platform plataforma -t repo:tag contexto

Dockerfile + contexto → imagen. plataforma es la del nodo, no la de tu Mac.

docker tag repo:tag registry/repo:tag

Un segundo nombre para la misma imagen (mismo ID): el registry va dentro del nombre.

docker push registry/repo:tag

Sube las capas que faltan y termina con tag: digest: sha256:… size: ….

docker run -d --name nombre -p puerto_host:puerto_contenedor registry/repo@sha256:digest

Si la imagen no está local, run hace el pull; por digest, de exactamente ese contenido.

Ejemplo real · La cadena completa del gateway del C01

bash · zshreference/c01 (gateway/ y k8s/gateway.yaml) y el ciclo diario de la hoja de comandos
# Desde reference/c01. El tag es el commit corto: sabes exactamente qué código corre
TAG=$(git rev-parse --short=7 HEAD)
REG=123456789012.dkr.ecr.us-east-1.amazonaws.com

# 1) Dockerfile + contexto → imagen, para los nodos x86 (no para tu Mac)
docker build --platform linux/amd64 -t classifier-gateway:$TAG gateway/

# 2) Segundo nombre con el registry delante: mismo IMAGE ID, nada se copia
docker tag classifier-gateway:$TAG $REG/classifier-gateway:$TAG

# 3) Login y push: la última línea trae el digest (3f9c2ab: digest: sha256:… size: …)
aws ecr get-login-password --region us-east-1 | docker login --username AWS --password-stdin $REG
docker push $REG/classifier-gateway:$TAG

# 4) En otra máquina: pull por digest y run (run también hace el pull si falta)
docker pull $REG/classifier-gateway@sha256:9b1c…
docker run -d --name gw -p 8080:8080 -e MODEL_NAME=classifier $REG/classifier-gateway@sha256:9b1c…

# 5) El contenedor: ¿corre y está sano?
docker ps --filter name=gw
curl -i localhost:8080/healthz
  • El tag es el commit (git rev-parse --short=7 HEAD): de un contenedor llegas al código exacto. Es el mismo classifier-gateway:3f9c2ab de k8s/gateway.yaml.
  • --platform linux/amd64: sin él, tu Mac construye arm64 y el nodo x86 no la puede ejecutar.
  • docker tag no duplica nada: docker images muestra el mismo ID con dos nombres.
  • El push imprime el digest; desde ahí, pull y run van por @sha256: (sección 11). 9b1c… está recortado: el real tiene 64 caracteres.
  • En tu Mac, correr la imagen amd64 imprime WARNING: The requested image's platform (linux/amd64) does not match the detected host platform (linux/arm64/v8): corre emulada; sirve para probar, no para medir latencia.

Cómo recordarla

Cuatro cosas, cinco verbos: Dockerfile → build → imagen → tag y push → registry → pull y run → contenedor.

Trampa

Hacer docker push classifier-gateway:3f9c2ab sin el host delante: sin registry en el nombre, Docker apunta a Docker Hub (docker.io/library/classifier-gateway), no a tu ECR.

Anatomía de un Dockerfile

¿Qué escribes, en qué orden y por qué?

Sintaxis con variables

FROM imagen:tag AS etapa

Cada FROM abre una etapa limpia; AS le da nombre para COPY --from.

COPY --from=etapa origen destino

Sin --from copia del contexto, y los archivos quedan de root; con --from, BuildKit conserva el dueño que tenían en esa etapa. --chown fija otro.

ENV VAR=valor

Persiste en la imagen y en cada contenedor. ARG, en cambio, vive solo durante el build.

CMD ["ejecutable", "arg", "…"]

Forma exec: lista JSON con comillas dobles, y tu proceso es el PID 1. ENTRYPOINT y CMD en detalle: sección 5.

Ejemplo real · El Dockerfile del gateway de C01

Dockerfilereference/c01/gateway/Dockerfile (todas las instrucciones; sin los comentarios)
# syntax=docker/dockerfile:1
FROM python:3.13-slim AS builder
ENV PIP_NO_CACHE_DIR=1 PIP_DISABLE_PIP_VERSION_CHECK=1
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
COPY requirements.txt .
RUN pip install --only-binary=:all: -r requirements.txt

FROM python:3.13-slim AS runtime
ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PATH="/opt/venv/bin:$PATH"
RUN groupadd --system --gid 10001 app && \
    useradd --system --uid 10001 --gid app --no-create-home --shell /usr/sbin/nologin app
WORKDIR /srv
COPY --from=builder /opt/venv /opt/venv
COPY app/ ./app/
USER 10001
EXPOSE 8080
HEALTHCHECK --interval=10s --timeout=2s --start-period=10s --retries=3 \
    CMD ["python", "-c", "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8080/healthz', timeout=1)"]
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8080", "--workers", "1", \
     "--timeout-keep-alive", "75", "--no-access-log", "--timeout-graceful-shutdown", "20"]
  • Dos FROM, dos etapas: builder arma el venv; runtime arranca de una slim limpia y solo recibe /opt/venv por COPY --from=builder.
  • ENV PATH="/opt/venv/bin:$PATH" en las dos etapas: así se encuentra el uvicorn del venv; sin eso, el contenedor sale con 127.
  • COPY requirements.txt . y pip install van antes de COPY app/: editar el código no reinstala las 37 dependencias (sección 2).
  • groupadd y useradd crean el UID 10001 y USER 10001 lo activa; COPY app/ sin --chown deja el código de root: el proceso lo lee pero no lo modifica.
  • EXPOSE 8080 solo documenta. El HEALTHCHECK usa Python porque la slim no trae curl, y Kubernetes lo ignora (allá mandan las probes).
  • CMD en forma exec con --workers 1: uvicorn es el PID 1 y recibe el SIGTERM (sección 5).

Cómo recordarla

Léelo en dos tiempos: lo que corre en build (FROM, RUN, COPY, ARG) arma el filesystem; lo que vale en run (ENV, USER, WORKDIR, HEALTHCHECK, CMD) es la configuración con la que arranca el contenedor.

Trampa

Creer que EXPOSE 8080 abre el puerto: sin -p 8080:8080 nada llega desde tu Mac. Y comentar al final de una instrucción (FROM python:3.13-slim # base): en un Dockerfile, # solo es comentario al inicio de la línea.

Capas, caché y .dockerignore

¿Por qué cambiar una línea a veces reconstruye todo, y cómo lo evitas?

Sintaxis con variables

COPY archivo_deps .

Primero solo el archivo de dependencias: esta capa cambia cuando cambian las dependencias, no cuando cambia el código.

Cache mount: si la capa se rehace, pip reusa lo que ya bajó. No lo combines con PIP_NO_CACHE_DIR=1, que apaga ese cache.

COPY código destino

El código al final: cambia en cada commit y solo invalida lo que viene después.

Build desde cero: --pull trae la base más reciente y --no-cache rehace cada paso.

Sintaxis con variables

CMD ["ejecutable", "arg"]

Forma exec: lista JSON con comillas dobles. Docker ejecuta el programa sin shell y ese proceso es el PID 1.

CMD ["arg"]

Script de entrada (ENTRYPOINT ["/entrypoint.sh"]): prepara y, con exec, le cede el PID 1 al CMD.

docker run --init --stop-timeout segundos imagen

Trampa

la forma exec no basta si tu proceso no maneja SIGTERM. Python no instala un handler (solo convierte SIGINT en KeyboardInterrupt), así que un script propio como PID 1 ignora docker stop y muere a los 10 s con 137. Y la forma shell no falla igual en todas las bases: en Debian y Ubuntu, /bin/sh (dash) se queda como PID 1; en Alpine (busybox) y donde /bin/sh es bash, sh -c suele hacer exec del último comando y tu proceso queda como PID 1 por casualidad: basta un pipe (|) para que deje de serlo.

  • EXPOSE 8080 en el Dockerfile del gateway solo documenta; lo que abre el puerto es "8080:8080". Y su CMD lleva --host 0.0.0.0 para que ese puerto llegue al proceso.
  • Los puertos van entre comillas porque el spec de Compose recomienda escribirlos siempre como string: YAML puede leer xx:yy como un número en base 60.

Cómo recordarla

-p es host:contenedor y solo sirve para entrar desde afuera; entre contenedores usas servicio:puerto del contenedor en una red con nombre (Compose ya crea una). Adentro, localhost es el propio contenedor y el servidor escucha en 0.0.0.0.

Trampa

-p 8080:8080 sin IP publica en todas las interfaces. Docker Desktop deja ese puerto accesible desde tu red local, y en un servidor Linux la referencia de Compose advierte que así se saltan las reglas del firewall del host. Publica lo interno (Prometheus, una base, un notebook) en 127.0.0.1. Y desde tu Mac no llegas a la IP de un contenedor, porque el bridge vive dentro de la VM: usa el puerto publicado.

Cómo recordarla

Trampa

tu Mac no es buen juez de permisos. En Docker Desktop, un bind mount pasa por el sistema de archivos compartido de la VM y los dueños no se comportan como en Linux: lo que funciona en tu laptop puede fallar en el servidor Linux, donde el UID 10001 del contenedor no coincide con el dueño de la carpeta del host. Valida con volúmenes nombrados (viven en la VM, con permisos de Linux de verdad) o en CI sobre Linux. Y en Mac, los bind mounts con miles de archivos chicos (un venv, un dataset de imágenes) son lentos: ponlos en un volumen.

  • python:3.13-slim es un índice multi-plataforma: el mismo FROM baja la variante arm64 en tu Mac y la amd64 con --platform linux/amd64 o en CI.
